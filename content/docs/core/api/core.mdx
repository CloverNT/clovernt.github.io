## 错误处理

框架统一返回 `Expected<T>`，而不是抛异常。成功时持有 `T`，失败时持有 `Error`。

```cpp
auto result = Plugin::PluginManager::loadPlugin("SomeJsPlugin");
if (!result) {
    logger().error("[{}] {}", result.error().code, result.error().message);
    return;
}
```

<TypeTable
  type={{

    Error: {
      type: 'struct { ErrorCategory category; std::int32_t code; std::string message; std::optional<std::int64_t> nativeCode; }',
      description: 'category 说明错误出在哪个模块，code 是该类别下的错误码，nativeCode 是系统返回的原始错误码（如果有）',
    },
    ErrorCategory: {
      type: 'enum class : std::uint8_t',
      description: 'General、Argument、Filesystem、System、DynamicLibrary、Module、Plugin、Event、Memory、Logger、Json',
    },
    CommonErrorCode: {
      type: 'enum class : std::int32_t',
      description: 'Unknown = 0、InvalidArgument、NotFound、AlreadyExists、InvalidState、OperationFailed、NotLoaded、AlreadyLoaded、Inactive、Unsupported、CallbackFailed、ParseFailed',
    },
  }}
/>

需要注意，`code` 不一定是 `CommonErrorCode`。

`category` 是 `Memory` 的错误，`code` 是 [`Memory::ErrorCode`](/docs/core/api/memory) 的值。

而系统调用失败时，`code` 往往就是系统错误码。

所以建议先看 `category`，再解释 `code`。

```cpp title="惯用写法"
Expected<Config> loadConfig(std::filesystem::path const& path) {
    std::ifstream file(path);
    if (!file) {
        return unexpected(ErrorCategory::Filesystem, CommonErrorCode::NotFound,
                          "config not found: " + path.string());
    }
    try {
        return parse(file);
    } catch (...) {
        return unexpected(fromCurrentException(ErrorCategory::Json, CommonErrorCode::ParseFailed));
    }
}
```

### 硬件异常

访问违例、除零这类硬件异常，正常情况下会直接让进程崩掉。

我们提供了 `guardVeh` 和 `guardSeh`，可以把它们转成 C++ 异常：

```cpp
try {
    const auto value = guardVeh([&] { return *reinterpret_cast<int*>(address); });
} catch (const StructuredException& e) {
    logger().error("fault: {} at {:#x}", faultKindName(e.kind()), e.faultAddress().value_or(0));
}
```

<Callout type="warn">
  这些异常捕获能处理的是无副作用的错误，但是无法处理之后状态已经被破坏的情况，例如栈溢出。
</Callout>

<Callout type="info">
  有人会提到在 Windows 上的 `/Eha`，但是 CloverCore 没有使用它。
  不使用的原因是 clang 对此的实现不完善，且这是一个非标准扩展。
</Callout>

调用你插件的 `load()` 和 `unload()` 时，外面包的就是 `guardVeh`。

### LIBRARY_ENTRYPOINT

`raw` 插件没有 `clovernt_plugin_load` 这样的入口，CloverLoader 只是把它加载进来。

这个宏帮你生成"被加载"和"被卸载"时该走的入口：

<Tabs items={['Windows', 'Linux']}>
  <Tab value="Windows">

  生成 `DllMain`。

  `DLL_PROCESS_ATTACH` 时先调用 `DisableThreadLibraryCalls`，再调用 `NAMESPACE::LOAD_FUNC(hModule)`。  
  `DLL_PROCESS_DETACH` 时调用 `NAMESPACE::UNLOAD_FUNC(hModule)`。

  </Tab>
  <Tab value="Linux">

  生成一个 `constructor` 函数：先清掉环境变量 `LD_PRELOAD`，再调用 `NAMESPACE::LOAD_FUNC(nullptr)`。

  由于 Linux 在动态链接库上的各种奇异搞笑的生命周期，所以 `UNLOAD_FUNC` 实际不会被调用。

  </Tab>
</Tabs>

```cpp
namespace MyRaw {
void Load(ModuleHandle) { /* ... */ }
void Unload(ModuleHandle) { /* ... */ }
}

LIBRARY_ENTRYPOINT(MyRaw, Load, Unload);
```

<Callout type="warn">
  Windows 上 `DLL_PROCESS_ATTACH` 是**在加载器锁里**执行的。
  
  别在 `LOAD_FUNC` 里做会再加载别的 DLL、或者要等别的线程的事，否则容易死锁。
  
  CloverCore 自己的做法是在入口里只做初始化，然后注册回调，等 Node 环境就绪再干活。
</Callout>
